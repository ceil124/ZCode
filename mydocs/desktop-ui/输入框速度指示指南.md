# 输入框速度指示指南

入口：`../README.md`
相关专题：`desktop-ui/架构与文件地图.md`（进程分层、状态所有者）
权威规范：仓库根 `DESIGN.md`（视觉令牌）/ `AGENTS.md`（架构约束）

> 目标：在 Composer 底部工具条右侧、发送键左侧（用户标注的红框位置）显示 `93 tok/s` 形态的解码速度指示，语义对齐 DSH（deepseek-harness）。

---

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| DSH 的 `93 tok/s` 是什么 | **会话累计解码吞吐**，不是瞬时速度；每个 step 收口时更新一次 |
| 计算公式 | `Σ outputTokens / (Σ decodeMs / 1000)`，其中 `decodeMs = assistant/message 时间 − 该 step 首个 token 时间` |
| 计入条件 | 只统计「同时有首 token 时间 **且** provider 报了 `usage.outputTokens`」的 step |
| ZCode 现有数据 | 渲染端：有 `usage.cumulative.outputTokens`（累计），**无任何时间**；CLI：有每请求 `durationMs` / `timeToFirstContentMs` / `usage` |
| 推荐方案 | **方案 B：协议侧累加**（CLI 投影算 `decodeMs`/`decodeTokens`，渲染端只做除法与格式化） |
| 改动量 | **不大**：核心 3 个文件（协议 schema / CLI 投影 / 新增 UI 组件），合计约 8 个文件 + 文档 |
| 主要风险 | V4 snapshot 是冻结协议，新字段必须 additive + 默认值；`useComposerToolbarFit` 的自适应收缩需要一并回归 |

## 1. DSH 侧算法拆解

### 1.1 数据来源：会话事件（不是本地计时）

DSH 用**事件流里的时间戳**，不是 `performance.now()` 本地计时：

| 事件 | 取用字段 | 用途 |
| --- | --- | --- |
| `step/start` | `time`, `turn`, `step` | step 起始时刻 `startTime` |
| `assistant/attempt` | `stream` | 首个 token 时刻（`assistantStreamFirstTokenTime`） |
| `assistant/message` | `time`, `usage`, `stream` | step 收口时刻 + provider 报的 `outputTokens` |
| `tool/call` / `tool/result` | `time`, `callId` | 工具耗时（与本功能无关，同属该投影） |

首 token 判定不是「第一个 chunk」，而是**第一个非空内容 delta**（`isTokenDelta`：text / reasoning / tool-args 增量，纯空白不算）。

### 1.2 折叠公式（两处实现，语义一致）

**持久化投影**（会话级，作为权威值下发）——`packages/session/session-stats/src/projection.ts:145-166`：

```ts
case 'assistant/message': {
  const firstToken = open.firstTokenTime ?? assistantStreamFirstTokenTime(event.data.stream) ?? null
  const next = { ...state, llmMs: state.llmMs + Math.max(0, event.time - open.startTime), openStep: null }
  if (firstToken !== null) {
    next.ttftMs += Math.max(0, firstToken - open.startTime)      // TTFT 单独累加
    next.ttftSteps += 1
    const outputTokens = usageOutputTokens(event.data.usage)
    if (outputTokens !== null) {
      next.decodeMs += Math.max(0, event.time - firstToken)       // ← 解码时间
      next.decodeTokens += outputTokens                            // ← 解码 token
    }
  }
  return next
}
```

**渲染端窗口折叠**（快照窗口内的降级兜底，字段名刻意与投影一致）——`packages/client/ui-chat/src/client/contract/turn-metrics.ts:85-95`：

```ts
if (reading.decodeMs !== null && reading.outputTokens !== null) {
  fold.decodeMs += reading.decodeMs
  fold.outputTokens += reading.outputTokens
  fold.sampled = true
}
// ...
if (fold.sampled && fold.decodeMs > 0) entry.tokensPerSecond = fold.outputTokens / (fold.decodeMs / 1000)
```

最终显示值——`packages/client/ui-chat/src/client/chat/StatsPills.tsx:145-149`：

```ts
const tps = stats.decodeMs > 0
  ? t('message.tokensPerSecond', { tps: formatTokensPerSecond(stats.decodeTokens / (stats.decodeMs / 1_000)) })
  : null
```

### 1.3 格式化与呈现

- `formatTokensPerSecond`（`message-chrome.ts:74-77`）：`>= 10` 取整，`< 10` 保留一位小数。
- 文案 `message.tokensPerSecond`（`locale.ts:85`）：`'{tps} tok/s'`。
- 挂载点：`conversation.composer.dock`，即 **Composer 下方**的一行（截图底部），与「N 轮 N 步」「10.7K tok · 缓存命中 74%」并排。

### 1.4 四个必须保住的语义

1. **累计而非瞬时**：分子分母都在整个会话（/ 窗口）上求和，不是滑动窗口速率。
2. **按 step 收口**：流式进行中的 step 不计入，所以数字在每次 step 结束时跳一次。
3. **同时具备才计入**：缺首 token 时间或缺 usage 的 step 整步丢弃（分子分母都不加），避免半数据污染比值。
4. **TTFT 与解码分离**：`ttftMs` 单独统计并展示，绝不混进 `decodeMs`——否则「首字慢」会被误算成「生成慢」。

## 2. ZCode 现状盘点

### 2.1 已经有的

| 能力 | 位置 | 说明 |
| --- | --- | --- |
| 会话累计输出 token | `packages/shared/src/zcode-protocol-v4/snapshot.ts:199-204`（`usage.cumulative.outputTokens`） | 渲染端**已在消费**，随快照下发 |
| 每请求耗时 + 首内容耗时 + usage | `apps/zcode-cli/packages/contracts/src/model/index.ts:209-221`（`ModelRequestCompletedStatusEvent`） | `durationMs` / `timeToFirstContentMs` / `usage` 三个都齐 |
| 该事件的产出点 | `apps/zcode-cli/packages/adapters/src/model/runner-stream.ts:176-211, 613` | `timeToFirstContentMs` = 请求开始 → 首个内容 |
| 该事件在 V4 层已被消费 | `apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/product-projection.ts:2362` | 目前只用来清重试标签，**payload 里已有全部所需字段** |
| TPS 计算函数 | `packages/shared/src/session-debug.ts:86-101`（`calculateOutputTps`） | 现成可复用，语义与 DSH 一致 |
| 累计值写入点 | `product-projection.ts:4529-4534`（`cumulative.outputTokens + ...`） | 每次 `ModelComplete` 累加 |
| 首 token 检测先例 | `packages/ui/src/v4/telemetry/localTtftObserver.ts:206-221` | 已在 `row.delta` 上做首输出判定（本地 TTFT 遥测） |
| 调试面已有 TPS | `packages/ui/src/DeveloperToolsPane.tsx:187-224` + `hooks/useSessionDebug.ts` | 1s 轮询 session-debug 通道，**调试专用**，不适合常驻 UI |

### 2.2 缺的是什么

**只缺一个东西：渲染端拿不到任何「时间」字段。**

`usage` 现在只有 `contextWindow { usedTokens, maxTokens, ... }` 和 `cumulative { inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens }`——全是计数，没有时间。而算吞吐必须要分母。

注意一个容易踩的坑：`cumulative.outputTokens` 是**跨整个会话累计**的。想只用渲染端数据凑公式，就必须在渲染端记「第一步首 token 的时刻」，也就是必须新增本地计时状态——这正是方案 A 的代价所在。

### 2.3 语义对照

| DSH | ZCode 对应物 | 差距 |
| --- | --- | --- |
| `step/start` 时间 | `model_request_started` 事件时间 | 有 |
| 首个非空 token 时间 | `timeToFirstContentMs`（请求开始 → 首内容） | 有，且是 provider 侧口径 |
| step 收口时间 | `durationMs`（请求总时长） | 有 |
| `usage.outputTokens` | `payload.usage.outputTokens` | 有 |
| 会话级 `decodeMs` / `decodeTokens` 累计投影 | — | **缺** |

所以 `generationDurationMs = durationMs − timeToFirstContentMs`，与本仓库调试面板已在用的口径**完全一致**（`session-debug.ts:105-106`）。

## 3. 三个方案

### 方案 A：纯渲染端本地计时（零协议改动）

在渲染端（`SessionPane` 或 `localTtftObserver` 旁）记本地时钟：首个 `row.delta` 到达时刻 → 该 step 的 `cumulative.outputTokens` 增量出现时刻，两者相减作分母。

- 优点：不动协议，改动最小，能做出「用时/速度」的本地体感。
- 缺点：
  - 本地时钟 = 端到端口径，**手机远控会掺入网络传输时间**，桌面 `desktop-continuous` 与手机 `web-remote-replayable` 两条链路数字不可比——违反 `AGENTS.md`「必须明确区分两条链路」的约束。
  - 刷新 / 重连 / 切会话后指标清零，不可回放；而 V4 快照是从事件日志重建的，其他所有统计量都能回放，只有这个不能 → 出现「同类指标语义不一致」。
  - 需要新引入一份 renderer-local 时间状态，等于第二份事实来源。

### 方案 B：协议侧累加（推荐）

CLI 在 V4 投影里按 `ModelNetworkStatus` 的 `model_request_completed` 累加 `decodeMs` / `decodeTokens`，随快照下发；渲染端只做除法 + 格式化。

- 优点：
  - 与 DSH 逐字段对齐，口径统一到单一时钟（CLI 侧 provider 请求边界）。
  - 渲染端无新增状态，刷新 / 重连 / 手机远控数字一致、可回放。
  - CLI 侧改动点已经存在（`product-projection.ts:2362` 那个 case 目前只清重试标签），payload 三个字段都齐。
  - 符合 `AGENTS.md`「避免重复状态和多条写入路径，明确唯一所有者」。
- 缺点：V4 snapshot 是冻结协议，需遵守 additive + 默认值规则；CLI 与渲染端要同批发布。

### 方案 C：复用 session-debug 通道（否决）

现成有 `tokensPerSecond`，但它是 1s 轮询的调试通道、需要额外的 per-session IPC 往返、字段在 `SessionDebugSnapshot` 里属调试面语义。常驻 UI 依赖它会造成「UI 读调试面」，架构上不可接受。

## 4. 方案 B 落点设计

### 4.1 数据契约（additive）

`packages/shared/src/zcode-protocol-v4/snapshot.ts` 的 `sessionUsageStateSchema` 增加一个可选块：

```ts
export const sessionUsageStateSchema = z.object({
  contextWindow: /* 不变 */,
  cumulative: /* 不变 */,
  // 解码吞吐原始量：整个会话累计。缺失 = 尚未有任何可计量的 step。
  // 刻意只下发原始量，除法与格式化留在渲染端（与 DSH 的 split 一致）。
  decode: z
    .object({
      decodeMs: z.number().nonnegative(),
      decodeTokens: z.number().nonnegative(),
      // 已计量 step 数；0 时渲染端不显示指示器。
      sampledSteps: z.number().int().nonnegative(),
    })
    .optional(),
})
```

**为什么不用 `tokensPerSecond: number`**：除法的四舍五入与文案归 UI；且保留原始量后，将来要做「本轮 / 全会话」切换或写进调试面都不用改协议。

### 4.2 状态所有者与事件顺序

```
CLI 进程（唯一所有者：@zcode/bootstrap 的 V4 投影）
├── 投影侧状态 decodeTotals: { decodeMs, decodeTokens, sampledSteps }
│   （与 contextWindowState 同级，随 fork/restore 一起 clone/restore）
│
├── onModelNetworkStatus(event)                       product-projection.ts:2362 附近
│   ├── type !== "model_request_completed"            → 原逻辑（清重试标签）
│   ├── !isMainTurn（querySource ≠ main_turn）        → 不累加，防 subagent 污染主会话
│   ├── durationMs / timeToFirstContentMs / usage.outputTokens 任一缺失 → 不累加
│   └── 全部具备 → decodeMs += max(0, durationMs − timeToFirstContentMs)
│                   decodeTokens += usage.outputTokens
│                   sampledSteps += 1
│                   → 追加一条 state.updated patch（usage.decode）
│
└── 冷快照 / seed：usage.decode 与 cumulative 一起从种子与当前快照取值
     │
     ▼  RPC（desktop-continuous / web-remote-replayable 两条链路走同一份投影）
渲染端
└── Composer 工具条读 snapshot.usage.decode → 除法 → formatTokensPerSecond → 渲染
```

**关键裁决：不要在 `onModelComplete` 里算。** 那条路径（`product-projection.ts:4505-4537`）虽然也处理主会话 usage，但 `ModelCompletePayload` **不带时间字段**（`contracts/src/events/session.events.ts:761-782`）。时间只在 `ModelRequestCompletedStatusEvent` 上，所以累加必须挂在 network status 这条路径上。两者都按 `main_turn` 过滤，语义对齐。

**幂等**：`model_request_completed` 每个 requestId 只应到达一次；如需强保证，可用 `Set<requestId>` 兜一次重放（会带来有界内存成本，需权衡）。同一 step 内 `llm/retry` 会产生多个 completed 事件——DSH 的口径是「重试后的那次」入账，这里按 requestId 分别入账，语义一致，但会在 UI 上体现为「重试把分母拉长」。若产品口径不接受，改为「同 step 只保留最后一次」需引入 step 级去重键（`turnId + step`），属可选项。

### 4.3 UI 落点（红框位置）

用户标注的红框在 **模型选择器 `GLM-5.3` 左侧**，正好是 `V4ComposerModelControls` 内部 `ChatContextUsage` 所在的位置（`V4ComposerToolbar.tsx:1013`）。两个候选：

| 选项 | 落点 | 视觉位置 | 是否需改 `ConversationComposer` |
| --- | --- | --- | --- |
| **1（对齐红框，推荐）** | `V4ComposerToolbar.tsx:1013` 之前（`ChatContextUsage` 左侧） | 模型簇最左，即截图红框 | 否，`usage` prop 已就位 |
| 2（严格「圆圈正左边」） | `ConversationComposer.tsx:2063` 之后 / `:2064` 之前 | 模型簇与发送键之间 | 是，需加 `submitControlNode` 的 useMemo 依赖 |

推荐选项 1：改动面更小，且与红框一致；若要严格贴住发送键，用选项 2。

**组件**：新建 `packages/ui/src/chat-input-toolbar/tokenSpeed.tsx`（与该目录下 `ThoughtLevelCycleControl.tsx` 等同类控件同址），内容极薄：

```tsx
// 纯展示：入参只有原始量 + locale，不含任何状态或副作用。
export function ComposerTokenSpeed({ decode, intl }: Props) {
  if (!decode || decode.sampledSteps === 0 || decode.decodeMs <= 0) return null;
  const tps = (decode.decodeTokens * 1000) / decode.decodeMs;
  return (
    <span className="inline-flex shrink-0 items-center text-ui-sm text-foreground-subtle tabular-nums"
          className="hidden @sm/composer:inline-flex"
          title={intl.formatMessage({ id: "chat.composer.tokensPerSecond.tooltip" })}>
      {intl.formatMessage({ id: "chat.composer.tokensPerSecond" }, { tps: formatTokensPerSecond(tps) })}
    </span>
  );
}
```

`formatTokensPerSecond` 直接移植 DSH 的 `>=10 取整 / <10 一位小数`（`message-chrome.ts:74-77`），可放在同一文件或 `packages/ui/src/v4/format.ts`。

### 4.5 边界与降级

| 场景 | 行为 |
| --- | --- |
| 新会话、无任何已收口 step | `decode.sampledSteps === 0` → 不渲染 |
| 请求全部失败 / provider 不报 usage | 不累加 → 指示器不出现（与 DSH 一致） |
| step 进行中（流式中） | 沿用上一次收口值，数字不跳；不在流式期间估算 |
| 只有工具调用、无文本输出 | 首 token 为 tool delta，仍计入（与 DSH 的 `isTokenDelta` 口径一致） |
| 旧版渲染端收到新快照 | 忽略未知字段，无副作用（additive） |
| 新版渲染端收到旧快照 | `usage.decode === undefined` → 不渲染 |
| 手机远控 / 远程会话 | 投影在 CLI 侧，两端数字一致 |
| 长时间会话 | `decodeMs` 会趋向「平均」，这是 DSH 的既有语义；若将来要「本轮速度」，在 `turnHeader` 上加本轮 `decode` 即可，不动现有字段 |

## 6. 如果只要「快」

只做方案 A：新增一个 renderer-local hook（挂在 `SessionPane`，观察 `row.delta` 首输出 + `usage.cumulative.outputTokens` 增量），组件与 UI 落点复用 4.3。改动收敛到 3 个文件（hook + 组件 + i18n），但要接受 4.5 中「刷新清零、手机远控数字不可比」两个已知语义缺口，并需在文档里明确标注为「本地体感值，非权威统计」。
