## 0. 快速结论

| 问题 | 答案 |
| --- | --- |
| 用什么更新器 | `electron-updater`，但 feed 换成自研 `ManifestUpdateProvider`（服务端下发 YAML manifest，非 latest.yml） |
| 检测接口 | `GET {endpointOrigin}/api/v1/releases/electron/manifest?platform=&device_mid=&channel=`，**后端实现，不在本仓库** |
| 版本比较在哪 | electron-updater 内部比较 `manifest.version` 与 `app.getVersion()`；main 只负责"已下载版本 vs 远端版本"的比较 |
| 检测的四个触发点 | 启动一次、每小时轮询、原生菜单手动检查、强制升级 gate |
| 谁会下载 | 只有 main。`autoDownload = false`，下载时机由 main 状态机决定 |
| Windows 会不会退出自动装 | 不会。`autoInstallOnAppQuit = process.platform !== "win32"` |
| Preview 包能更新吗 | 不能。`ZCODE_PRODUCT_FLAVOR !== "production"` 时 `initAutoUpdater` 直接被禁用 |
| 强更（阻塞启动）接口 | `GET /api/v1/client/configs?app_version=&platform=` → `data.configs.forceUpdate.minimalVersion` |

## 2. 如何检测新版本

### 2.1 Feed 注入

`autoUpdater.ts:754` `applyManifestUpdateProvider()` 在 `initAutoUpdater` 内调用一次：

```ts
autoUpdater.setFeedURL({
  provider: "custom",
  updateProvider: ManifestUpdateProvider,
  endpointOrigin: DEFAULT_ZCODE_ENDPOINT_ORIGIN,
  manifestUrl,                 // 仅未打包时可被覆盖
  releasePlatform,             // "windows-x86_64" | "darwin-aarch64" | "linux-x86_64" ...
  deviceMid,
  resolveEndpointOrigin,
  resolveReleaseChannel,       // 每次 check 现读 receivePreviewUpdates
});
```

覆盖入口 `resolveUpdateFeedSourceFromStartupConfig()`（`autoUpdater.ts:695`）：读 `--zcode-update-feed-url=` 或 `ZCODE_UPDATE_FEED_URL`。**`app.isPackaged` 时忽略并在日志中告警**——防止正式包被环境变量改道。

### 2.2 请求构造

`manifestUpdateProvider.ts`：

| 项 | 值 |
| --- | --- |
| 默认路径 | `/api/v1/releases/electron/manifest`（`ELECTRON_MANIFEST_API_PATH`，22 行） |
| Query | `platform`（如 `windows-x86_64`）、`device_mid`（有值才带）、`channel`（stable→`1`，preview→`3`） |
| Header | `Accept: application/x-yaml,text/yaml,text/plain,*/*`、`X-Platform`、`X-Release-Channel`、`X-Device-Mid` |
| 平台映射 | `win32→windows`；arch `arm64→aarch64`、`x64→x86_64`、`ia32→x86` |
| Range 请求 | `isUseMultipleRangeRequest = false`（对齐 OSS 返回 206 但 Content-Type 错误的行为） |

`getLatestVersion()`（205 行）：请求 → `parseYaml` → 校验 `version` 为字符串，否则抛 `Invalid electron update manifest` → 返回 `{...parsed, zcodeReleaseChannel}`。

**`zcodeReleaseChannel` 是关键**：`update-available` 事件默认不带请求通道，main 无法识别"旧通道的迟到响应"，因此把本次请求通道随 `UpdateInfo` 带回去（源码 235–238 行注释）。

### 2.3 版本比较与文件选择

- **是否"有新版本"**：由 electron-updater 内部比较 `manifest.version` 与 `app.getVersion()`。开发态可用 `--zcode-auto-update-dev-version=` 伪造当前版本（`getCurrentAppVersionForUpdate()`）。
- **是否下载**：`shouldDownloadAvailableUpdate(version)`（`autoUpdater.ts:216`）——`!readyUpdateVersion || semver.gt(远端, ready)`。没有这一步，已 ready `3.1.2` 时会重复下载 `3.1.3`（源码 1498–1501 行注释）。
- **下载哪些文件**：`resolveFiles()`（`manifestUpdateProvider.ts:242` → `resolveManifestFiles`）
  - Linux 按实际安装器类型过滤扩展名：`AppImageUpdater→.appimage`、`DebUpdater→.deb`、`RpmUpdater→.rpm`、`PacmanUpdater→.pkg.tar.zst|.pacman`
  - 缺 `sha512`/`sha2` 直接抛错
  - 缺当前安装格式直接抛错（`Manifest contains no update file for ...`），**禁止跨安装格式更新**
  - `packages[process.arch]` → `packageInfo.path` 解析为绝对 URL（差分更新用）

### 2.4 触发时机

| 触发 | 入口 | 约束 |
| --- | --- | --- |
| 启动 | `initAutoUpdater` 末尾 `triggerCheckForUpdates("startup")`（1756） | 不阻塞主界面 |
| 轮询 | `setInterval(..., AUTO_UPDATE_POLL_INTERVAL_MS)`，常量 `60 * 60 * 1000`（26 行），`unref()` | 仅 `idle` / `update-downloaded` 态进入（`canPollForUpdatesFromState`），避免 checking/downloading 期间重复拉起同一轮 |
| 原生菜单手动检查 | `checkForUpdateMenuClick`（1837）← `desktopApplicationMenu` ← `desktopCommandHandlers:594` | 按当前 `menuState` 分支：`update-downloaded`→直接安装；`download-progress`→回 `already-downloading`；`update-available`→回 `available`；in-flight→回 error |
| 强制升级 | `requestForceAutoUpdate`（1764）← `forceUpdateGuard` → `forceUpdatePrompt` | 复用进行中的 check；按 `menuState` 直接进入对应阶段 |
| 设置变更 | `refreshAutoUpdaterReleaseChannel`（1352）← `syncAppSettings`（`main/index.ts:958`） | check 进行中则记入 `pendingManifestReleaseChannelRefresh` 延后；`download-progress`/`update-downloaded` 时跳过 |

**并发保护**：`checkForUpdatesInFlight` 布尔 + `beginAutoUpdateCheck()/finishAutoUpdateCheck()` generation（`autoUpdateCheckGeneration` / `checkId`）。陈旧结果通过 `settlingAutoUpdateCheckId` 与 `shouldIgnoreStaleAvailableUpdate(infoChannel)` 丢弃。

### 2.5 下载与安装策略

```ts
autoUpdater.autoDownload = false;                                  // 1501
autoUpdater.autoInstallOnAppQuit = process.platform !== "win32";   // 1505
```

- `autoDownload = false`：检测到新版本后 main 自己决定。顺序为：强更监听存在 → 立即下载；否则读 `autoDownloadAndInstallUpdates` 偏好 → 自动下载；否则停在 `update-available` 等用户点。
- Windows 关闭退出即装：NSIS 在窗口关闭后异步安装，若用户随即关机可能留下半更新状态（源码 1502–1504 行注释）。因此 Windows 必须用户显式触发 `QuitAndInstallUpdate`。

### 2.6 electron-updater 事件 → 状态机

| 事件 | 行号 | 处理要点 | 结果 `menuState` |
| --- | --- | --- | --- |
| `checking-for-update` | 1543 | — | `{ kind: "checking", enabled: false }` |
| `update-available` | 1548 | ① 通道陈旧检查 `shouldIgnoreStaleAvailableUpdate` ② `shouldDownloadAvailableUpdate` ③ 跳过版本检查 `isSkippedUpdateVersion` ④ 记录 release notes ⑤ 清伪 ready（`readyUpdateRestoredFromPendingReleaseNotes`） | `update-available` 或直接进入下载 |
| `update-not-available` | 1620 | 若已有 `readyUpdateVersion` 维持 downloaded，否则清空 | `update-downloaded` 或 `{ kind: "idle", enabled: true }` |
| `download-progress` | 1646 | 取消令牌失效则丢弃；`menuState` 非 downloading/available 则丢弃 | `download-progress`（含已下载/总大小） |
| `update-downloaded` | 1678 | 写 `readyUpdateVersion/_Channel/_ReleaseNotes`；持久化 pending release notes | `update-downloaded` |
| `error` | 1720 | `shouldIgnoreCancelledDownloadError` 忽略取消下载的迟到 error | 交给 `handleAutoUpdateFailure`（987）收敛 |

### 2.7 通道（stable / preview）

| 环节 | 位置 |
| --- | --- |
| 用户偏好来源 | 设置 `receivePreviewUpdates` |
| 请求前同步 | `syncAutoUpdateCheckChannelFromSettings`（733）：每次 check 前把 `availableUpdateChannel` / `activeAutoUpdateCheckChannel` 更新为目标通道 |
| Provider 内二次读取 | `resolveReleaseChannel` 回调（`applyManifestUpdateProvider` 内） |
| 用户实时切换 | `refreshAutoUpdaterReleaseChannel`（1352）经 `syncAppSettings` 即时通道（不等 setting 订阅） |
| 陈旧保护 | 旧通道 manifest 可能晚于新请求返回，用 `zcodeReleaseChannel` + `activeAutoUpdateCheckChannel` 判定丢弃 |

## 5. 强制升级（远端阻塞 gate）

| 环节 | 位置 |
| --- | --- |
| 调用时机 | `main/index.ts:2188`，条件 `ZCODE_PRODUCT_FLAVOR === "production" && app.isPackaged` |
| 接口 | `GET {origin}/api/v1/client/configs?app_version={ZCODE_VERSION}&platform={platform-arch}` |
| 取字段 | `getForceUpdateMinimalVersionFromClientConfig`（`forceUpdateGuard.ts:50`），要求 envelope `code === 0` |
| 判定 | `resolveForceUpdateRequirement`（`packages/shared/src/forceUpdate.ts:119`）→ 比较当前版本与 `minimalVersion` |
| 拦截表现 | `showForceUpdatePrompt`（`forceUpdatePrompt.ts`）：480×256 独立窗口，内联 HTML，三按钮「自动升级 / 手动升级 / 退出」；`onBlocked` 回调置 `forceUpdateMainWindowCreationBlocked`，主窗口不创建 |
| 容错 | 请求超时 10s、响应上限 1MB、配置解析失败一律 fail-open（不阻塞） |
| dev 跳过 | 未打包时跳过（源码 2181–2187 注释：feature 分支不 bump 版本号，会被线上 `minimalVersion` 误判为需强更而启动秒退） |

强更与常规更新的衔接：`requestForceAutoUpdate` 复用同一 `autoUpdater` 实例与 `menuState`，因此强更期间到达的 `update-available` 会优先走 `downloadAvailableUpdate("force-update")`（1597–1600）。

## 10. 排查线索

| 现象 | 原因 |
| --- | --- |
| 打包态设置 `ZCODE_UPDATE_FEED_URL` 无效 | 按 `isPackaged` 主动忽略（`resolveUpdateFeedSourceFromStartupConfig` 设计如此），日志有告警 |
| 切换"接收预览版"后没有立即重新检查 | `refreshAutoUpdaterReleaseChannel` 在 `download-progress` / `update-downloaded` 态会 skip；check 进行中则 defer 到收口 |
| 取消下载后界面又回到"下载中" | 陈旧 `download-progress` 应被 `downloadCancellationToken.cancelled` 拦掉；迟到 `error("cancelled")` 由 `shouldIgnoreCancelledDownloadError` 忽略 |
| Windows 下载完成没有自动安装 | `autoInstallOnAppQuit = false`（by design），必须显式 `QuitAndInstallUpdate` |
| Linux 报 `Manifest contains no update file for ...` | manifest 未提供当前安装格式的产物（deb / rpm / pacman / appimage），跨格式更新被主动禁止 |
| 弹窗显示了旧通道的版本 / 旧 release notes | 通道陈旧检查失效：查 `zcodeReleaseChannel` 是否随 `UpdateInfo` 正确带回，以及 `activeAutoUpdateCheckChannel` |
| 更新按钮一直"重启以更新"但点菜单不安装 | `checkForUpdateMenuClick` 在 `update-downloaded` 态会直接 `quitAndInstallUpdate()`；若未生效查 ready 状态是否被 `clearReadyUpdateState` 清过（伪 ready 场景） |
| Preview 包完全没有更新入口 | 预期行为：`ZCODE_PRODUCT_FLAVOR !== "production"` 时更新器整体禁用 |
| 更新后版本说明弹窗重复出现 | 查 `acknowledgedPostUpdateReleaseNotesVersions` 与 `clearPersistedPostUpdateReleaseNotesForVersion`（936）的持久化清理 |
